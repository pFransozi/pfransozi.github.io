Hoje paramos no esquema relacional

Ainda não é necessário escrever CREATE TABLE. Primeiro precisamos decidir corretamente quais relações existirão, quais atributos pertencem a cada uma e como as chaves conectam essas relações. A implementação em SQL virá depois.

Primeiro passo do mapeamento

Comece por uma entidade antes de tratar os relacionamentos

Para entender a passagem do DER para o esquema relacional, vamos primeiro isolar uma entidade forte. Nesse caso, o mapeamento pode ser feito em três decisões simples: criar a relação, levar os atributos e definir a chave primária.

1 · Entidadecria a relação

Cada entidade forte dá origem a uma relação que representa o mesmo tipo de objeto no esquema relacional.

SALA → SALA(...)
2 · Atributospreenchem a relação

Os atributos simples da entidade passam a aparecer como atributos da relação correspondente.

nome · capacidade
3 · Identificadordefine a chave primária

O atributo usado no DER para distinguir cada ocorrência passa a identificar cada tupla da relação.

id_sala → PK

Observe a mudança de linguagem. No DER falamos em entidade; no modelo relacional falamos em relação. Na implementação, essa relação normalmente será criada como uma tabela. Nesta aula usaremos “relação” quando estivermos descrevendo o modelo lógico.

Segundo passo do mapeamento

Retome a classificação dos atributos antes de decidir como mapeá-los

Na Aula 04, usamos diferentes exemplos para observar a estrutura, a quantidade de valores e a origem de um atributo. Agora vamos recuperar os mesmos exemplos e perguntar o que acontece com cada um quando passamos para o modelo relacional.

i
As classificações continuam se combinando. Um atributo pode ser, ao mesmo tempo, simples, monovalorado e armazenado. O objetivo agora não é criar novas categorias, mas usar o que já vimos para orientar o mapeamento.
Estrutura · simplesMapeamento direto

Como capacidade é tratada como uma unidade, ela pode aparecer diretamente na relação SALA.

SALA.capacidade → capacidade
Estrutura · compostoLeve os componentes simples

Quando um atributo foi dividido em partes significativas, são essas partes que aparecem no esquema relacional.

endereço → logradouro, número, cidade, CEP
Quantidade · monovaloradoUm valor por ocorrência

Se cada usuário possui uma única data de nascimento, esse valor pode ser mantido como atributo da relação.

USUÁRIO.data_nascimento → data_nascimento
Quantidade · multivaloradoVários valores exigem outra estrutura

Um usuário pode possuir vários telefones. Por isso, não basta reservar uma única posição para telefone na relação USUARIO.

USUÁRIO.telefone = {41..., 41...} → relação própria
Origem · armazenadoO valor pode ser registrado

A data de nascimento é um fato informado pelo domínio e pode ser armazenada diretamente.

data_nascimento = 15/03/2002
Origem · derivadoNem todo valor precisa ser armazenado

Se um valor pode ser obtido a partir de outros dados, precisamos avaliar se faz sentido guardá-lo ou calculá-lo quando necessário.

idade ← data_atual − data_nascimento

O que muda quando passamos para o modelo relacional?

Atributos simples, monovalorados e armazenados tendem a seguir diretamente para a relação. Atributos compostos são representados por seus componentes. Atributos multivalorados exigem uma relação própria. Já atributos derivados precisam ser avaliados: se podem ser calculados a partir de dados já armazenados, não precisam necessariamente ocupar um atributo persistido.

Não force vários valores dentro de uma única relação

No caso de USUÁRIO.telefone, evite soluções como telefone1, telefone2 e telefone3 ou uma lista inteira dentro de um único atributo. O fato de o telefone ser multivalorado é justamente a pista de que precisaremos representá-lo de outra forma.

O que ainda está faltando?

Essas duas relações armazenam os dados próprios de usuários e salas, mas ainda não preservam o fato de que um usuário realiza reservas de uma sala. O próximo passo é transformar os relacionamentos do DER.
