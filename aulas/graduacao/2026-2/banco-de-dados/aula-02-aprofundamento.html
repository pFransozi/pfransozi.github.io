Parte I · Do arquivo ao sistema compartilhado

O problema não é o arquivo. É quem precisa coordenar o conjunto.

Arquivos continuam sendo mecanismos úteis de persistência. A mudança de escala acontece quando dados relacionados passam a sustentar várias operações, aplicações, regras e usuários ao mesmo tempo.

Arquivos resolvem persistência; não resolvem automaticamente coordenação

Guardar um conjunto de dados em CSV, JSON, texto ou outro formato pode ser uma solução adequada quando o problema é simples e delimitado. O sistema operacional já fornece mecanismos para criar, ler, alterar e remover arquivos. Para muitos artefatos (configurações, exportações, documentos, logs, intercâmbio de dados ou pequenos conjuntos controlados por uma única aplicação), isso pode ser suficiente.

Em um software, podemos chamar de estado o conjunto de valores que representa a situação do sistema em determinado momento. Por exemplo, quais clientes estão cadastrados, quais pedidos estão abertos, quais pagamentos foram realizados e quanto existe de cada produto em estoque. O problema começa a mudar de escala quando esse estado deixa de ser controlado por uma única rotina e passa a ser consultado e modificado por diferentes partes do sistema. Se essas informações estiverem espalhadas por arquivos diferentes, cada programa que os acessa precisa conhecer formatos, nomes, regras, locais de armazenamento e procedimentos de atualização. A lógica de persistência começa a se repetir dentro das próprias aplicações.

Os sintomas do crescimento

Silberschatz, Korth e Sudarshan usam sistemas baseados em arquivos para mostrar por que os sistemas de banco de dados surgem. À medida que novas aplicações são adicionadas, aparecem problemas recorrentes: redundância e inconsistência, dificuldade de acesso, isolamento dos dados, regras de integridade espalhadas, dificuldade de garantir atomicidade em falhas, conflitos de acesso simultâneo e controle de segurança fragmentado.

Redundância e inconsistência

A mesma informação pode ser copiada para arquivos diferentes. Se apenas uma cópia for atualizada, o sistema passa a representar versões incompatíveis do mesmo fato.

Isolamento

Dados relacionados ficam separados por formatos e arquivos distintos, aumentando o trabalho necessário para combiná-los e responder novas perguntas.

Regras distribuídas

Validações como “um saldo não pode ficar inválido” ou “um pedido precisa referenciar um cliente existente” acabam implementadas em vários programas.

Concorrência e falhas

Quando duas operações alteram o mesmo estado ou uma atualização é interrompida pela metade, é necessário coordenar o que pode ser considerado válido.

Banco de dados e SGBD não são sinônimos

Um banco de dados é a coleção organizada de dados relacionados que representa parte de um domínio. Um Sistema Gerenciador de Banco de Dados (SGBD) é o software responsável por definir, armazenar, consultar, modificar, proteger, compartilhar e recuperar essa coleção de forma controlada.

Essa distinção parece terminológica, mas é estrutural. O banco de dados mantém de forma persistente parte do estado relevante para o sistema; o SGBD fornece a infraestrutura para organizar e administrar esses dados. PostgreSQL, MySQL, Oracle Database e SQL Server são exemplos de SGBDs. As tabelas, registros, restrições e demais estruturas existentes dentro de um banco específico não são o SGBD.

Ideia-chave

O ganho central de um SGBD não é simplesmente “guardar em tabelas”. É retirar de cada aplicação parte da responsabilidade de coordenar estrutura, acesso, integridade, concorrência, segurança e recuperação.

Arquivos continuam adequados

Escolher um banco de dados para qualquer persistência também pode aumentar complexidade desnecessariamente. A decisão depende das informações que o sistema precisa manter ao longo do tempo e das garantias exigidas sobre esse estado.

Parte II · A abordagem de banco de dados

Um SGBD conhece a estrutura dos dados e coordena seu uso.

Uma das diferenças fundamentais entre uma coleção de arquivos e a abordagem de banco de dados é a presença de uma camada gerenciadora que conhece a estrutura do banco e oferece serviços compartilhados sobre ela.

Uma base autodescritiva

Elmasri e Navathe destacam como característica da abordagem de banco de dados a natureza autodescritiva do sistema. Além dos valores usados pelas aplicações, o SGBD mantém informações que descrevem as próprias estruturas: nomes de objetos, atributos, tipos, restrições, relacionamentos e outras propriedades. Essas descrições compõem os metadados e são armazenadas em um catálogo ou dicionário de dados.

Isso permite que ferramentas e componentes do próprio SGBD inspecionem o banco sem depender de um programa específico escrito para cada arquivo. A descrição da estrutura passa a fazer parte do próprio sistema de banco de dados, em vez de permanecer espalhada e implícita no código das aplicações.

Separação entre programa e dados

Em sistemas fortemente baseados em arquivos, é comum que o programa conheça diretamente o formato físico dos registros. Alterar a estrutura de um arquivo pode exigir alterar todos os programas que o interpretam. A abordagem de banco de dados procura reduzir esse acoplamento usando esquemas, mapeamentos e mecanismos de abstração.

Isso não significa que uma aplicação nunca precise mudar quando o banco evolui. Significa que o sistema é organizado para que diversas mudanças possam ser absorvidas em camadas mais baixas ou em interfaces controladas, preservando consumidores sempre que possível.

Múltiplas visões sobre os mesmos dados

Usuários e aplicações diferentes não precisam enxergar todo o banco da mesma forma. Um atendente pode precisar apenas de dados de contato e situação de um pedido; um financeiro pode precisar de pagamentos; uma rotina de análise pode precisar de informações agregadas. A ideia de visão externa permite representar subconjuntos ou formas específicas de apresentação sobre uma mesma base lógica.

Compartilhamento com controle

Quando vários usuários ou processos acessam o mesmo banco, o SGBD precisa coordenar essas operações para evitar conflitos e preservar a consistência dos dados. Transações, controle de concorrência e recuperação serão estudados mais adiante no curso; neste momento, importa perceber por que esses mecanismos pertencem à infraestrutura de dados e não deveriam ser reinventados isoladamente por cada aplicação.

Uma mudança de responsabilidade

Com arquivos, a aplicação frequentemente implementa grande parte da coordenação. Com um SGBD, várias responsabilidades passam a ser serviços comuns, reutilizados por diferentes aplicações.

Não confunda SQL com SGBD

SQL é uma linguagem usada em sistemas relacionais para definir e manipular dados. Um SGBD implementa a linguagem e também oferece catálogo, armazenamento, segurança, transações, recuperação, otimização e outros mecanismos.

Base conceitual

Elmasri & Navathe, seções sobre características da abordagem de banco de dados e arquitetura de sistemas.

Parte III · Abstração e arquitetura

Do domínio ao armazenamento, cada nível responde a uma pergunta diferente.

Para compreender a abstração em banco de dados, podemos separar três perguntas. O que da realidade queremos representar? Essa é a questão do domínio observado. Como esses dados serão organizados? Essa é a questão da estrutura lógica. Como o SGBD armazenará e acessará esses dados? Essa é a questão do armazenamento físico. A abstração permite trabalhar com uma dessas perspectivas sem precisar lidar, ao mesmo tempo, com todos os detalhes das demais.

Todo dado é uma representação

Machado apresenta a abstração como o processo de concentrar a atenção nas propriedades relevantes de uma realidade e deixar de lado detalhes que não são importantes para o contexto em análise. Antes de existir tabela, documento ou arquivo, existe um minimundo: a parte da realidade que o sistema pretende representar.

Um cliente real não é uma linha em uma tabela. A linha é uma representação construída para atender necessidades do sistema. Nome, CPF, endereços, preferências, contratos e eventos são selecionados porque algumas perguntas e operações exigem essas informações. Outras características do cliente ficam fora do modelo.

Do domínio para o projeto: conceitual, lógico e físico

As três perguntas anteriores podem ser refinadas durante o projeto. O modelo conceitual funciona como ponte entre o domínio observado e a solução técnica: identifica os conceitos relevantes e suas relações sem depender de um SGBD específico. O modelo lógico organiza essa representação de acordo com um modelo de dados (por exemplo, o relacional). O modelo físico concretiza a implementação considerando tipos suportados, índices, formatos, métodos de acesso e outras decisões do produto escolhido.

Essas perspectivas ajudam a não transformar limitações técnicas de uma ferramenta em características do próprio domínio. Primeiro precisamos compreender o que o sistema representa; depois decidimos como essa representação será estruturada e implementada.

Externo, conceitual e interno: perspectivas da arquitetura

Elmasri e Navathe apresentam a arquitetura de três esquemas, historicamente associada à ANSI/SPARC. Ela separa o que diferentes usuários enxergam, a estrutura lógica global do banco e a organização interna usada pelo SGBD.

Os três esquemas são descrições. Os dados efetivamente armazenados existem no nível físico, enquanto os níveis superiores fornecem abstrações que permitem manipular esses dados sem exigir conhecimento de todos os detalhes internos.

Uma distinção importante

“Conceitual, lógico e físico” descreve etapas ou perspectivas de projeto. “Externo, conceitual e interno” descreve níveis de uma arquitetura de banco de dados. As ideias se relacionam, mas não são duas listas de sinônimos.

Engenharia de Software

Abstração reduz acoplamento. Quando uma camada esconde detalhes desnecessários das camadas superiores, mudanças locais tendem a produzir menos impacto no restante do sistema.

Parte IV · Estrutura, estado e descrição

Esquema diz o que pode existir; instância mostra o que existe agora.

Separar estrutura, estado atual e metadados é essencial para entender como um SGBD descreve e administra um banco ao longo do tempo.

Esquema: a descrição relativamente estável

O esquema descreve a organização do banco: quais estruturas existem, quais propriedades elas possuem e quais restrições definem os estados válidos. Em um banco relacional, por exemplo, o esquema pode indicar que existe uma tabela cliente com determinadas colunas, tipos e chaves.

O esquema muda, mas normalmente em uma frequência muito menor que os valores armazenados. Adicionar um atributo, alterar uma restrição ou criar uma nova relação são mudanças de esquema.

Instância ou estado: os valores de um momento

A instância — também chamada, em alguns textos, de estado atual do banco — é o conjunto de valores armazenados em determinado instante. Inserir um novo cliente ou alterar o status de um pedido modifica a instância sem necessariamente mudar o esquema.

Metadados: dados que descrevem os dados

Os metadados registram descrições sobre os objetos do banco: nomes, tipos, restrições, propriedades e outras informações estruturais. O SGBD mantém esses metadados em seu catálogo ou dicionário de dados.

Quando uma ferramenta lista tabelas disponíveis ou quando o SGBD verifica que um valor deve respeitar determinado tipo, ela não precisa adivinhar a estrutura. Essa informação está registrada como parte da própria descrição do banco.

“Entrou um novo pedido” altera o estado. “Agora todo pedido precisa registrar a origem” altera a estrutura ou suas regras e, portanto, envolve o esquema.

Por que metadados importam?

O catálogo permite que o sistema conheça a própria estrutura e oferece uma base comum para validação, ferramentas, consultas administrativas e otimização.

Parte V · Independência de dados

A independência de dados reduz o impacto das mudanças entre camadas.

Independência de dados é a capacidade de alterar um esquema em determinado nível sem exigir mudanças correspondentes no nível superior. É uma forma específica de desacoplamento aplicada à arquitetura de dados.

Independência física

Independência física de dados é a capacidade de alterar o esquema interno sem exigir alterações no esquema conceitual. Criar ou reorganizar estruturas de acesso, alterar a forma como registros são distribuídos, compactar dados ou mudar detalhes de armazenamento pode melhorar desempenho e capacidade sem alterar a estrutura lógica percebida pelas aplicações.

Exemplo clássico

Um índice é uma estrutura adicional de organização mantida pelo SGBD para localizar dados com mais rapidez. Por exemplo, um índice pode ser criado para acelerar buscas por CPF. A aplicação continua consultando o mesmo atributo; o que muda é a maneira interna usada pelo SGBD para encontrar os registros.

Independência lógica

Independência lógica de dados é a capacidade de alterar o esquema conceitual preservando, quando possível, esquemas externos e programas de aplicação. Esse tipo de independência é mais difícil porque alterações lógicas podem mudar diretamente a estrutura que consumidores esperam encontrar.

Adicionar informações que não afetam consumidores existentes, reorganizar estruturas e oferecer uma visão compatível durante uma migração são estratégias que podem reduzir o impacto de mudanças lógicas. A arquitetura não elimina a necessidade de planejar evolução; ela oferece mecanismos para controlar essa evolução.

Independência não significa ausência de impacto

A arquitetura de três esquemas funciona como um ideal de separação. SGBDs reais implementam esses níveis de maneiras diferentes, e nem toda alteração pode ser escondida. Uma mudança que altera o significado de um dado ou remove algo consumido por uma aplicação provavelmente exige adaptação. O ponto é reduzir dependências desnecessárias e localizar mudanças tanto quanto possível.

Regra de engenharia

Quanto mais uma decisão de armazenamento fica confinada ao nível interno, menor tende a ser o impacto sobre a lógica de negócio. Quanto mais uma mudança altera o significado ou a estrutura visível dos dados, maior tende a ser o custo de compatibilidade.

Por que a lógica é mais difícil?

Alterações conceituais podem mudar objetos, atributos, relacionamentos e restrições utilizados diretamente pelas aplicações. Preservar contratos exige mapeamento, compatibilidade e migração planejada.

Base conceitual

Elmasri & Navathe, seção 2.2.2. A obra usa a arquitetura de três esquemas para formalizar independência lógica e física.

Parte VI · Modelos de dados e síntese

Um modelo de dados define uma maneira de estruturar e interpretar o estado.

Escolher um modelo não é escolher apenas uma marca de software. Modelos fornecem conceitos e estruturas para representar dados; SGBDs concretos implementam essas ideias com características próprias.

Modelo de dados não é produto

O modelo relacional não é PostgreSQL; o modelo documental não é MongoDB; o modelo de grafos não é Neo4j. Produtos são implementações concretas, enquanto modelos descrevem formas de organizar estruturas, vínculos, operações e restrições.

A mesma necessidade de negócio pode ser representada por modelos diferentes, mas o custo de certas consultas, regras e evoluções muda conforme a estrutura escolhida. Por isso, a decisão deve partir das propriedades do problema, e não apenas da familiaridade com uma ferramenta.

Relacional

Tabelas e relações

Organiza dados em relações compostas por atributos e tuplas, com forte tradição de integridade, consulta declarativa e transações.

Favorece: dados estruturados, relações bem definidas, consistência e consultas variadas.

Documental

Documentos agregados

Agrupa informações em documentos com estrutura que pode variar, aproximando dados que costumam ser lidos ou alterados juntos.

Favorece: agregados autocontidos, estruturas flexíveis e evolução de formatos.

Chave-valor

Acesso direto por chave

Associa uma chave a um valor e prioriza operações simples de recuperação ou atualização quando o identificador é conhecido.

Favorece: cache, sessões, preferências e estados acessados predominantemente por chave.

Grafos

Nós e conexões

Representa entidades e relacionamentos explicitamente, tornando a navegação por conexões parte central do modelo.

Favorece: redes, dependências, recomendações e perguntas baseadas em caminhos ou vizinhanças.

Por que começar pelo relacional?

O curso começa pelo modelo relacional porque ele fornece uma base rigorosa para discutir estrutura, integridade, consulta e projeto. Silberschatz, Korth e Sudarshan apresentam o modelo relacional logo após a introdução aos sistemas de banco de dados; Machado também o utiliza como núcleo para discutir relações, domínios, chaves e integridade.

Uma relação pode ser visualizada didaticamente como uma tabela. Cada coluna representa um atributo; cada linha, uma tupla; cada atributo possui um domínio de valores admissíveis; chaves permitem identificar tuplas e relacionar estruturas. Na próxima etapa da disciplina, esses termos serão tratados com mais precisão.

id_clientenomecidade
17AnaCuritiba
28RaviSão José dos Pinhais

Nesse pequeno exemplo, id_cliente, nome e cidade são atributos; cada linha representa uma tupla. O valor 17 não é “o cliente”; é parte de uma representação lógica escolhida para identificá-lo no sistema.

Escolha tecnológica como decisão de engenharia

Antes de escolher uma tecnologia, é útil caracterizar o estado que o software precisa manter: quais dados existem, como se relacionam, quem os acessa, quais consultas predominam, quais regras precisam ser garantidas, qual nível de concorrência é esperado e como o sistema deve reagir a falhas e evolução.

Não existe um modelo universalmente superior. Estruturas diferentes favorecem problemas diferentes. A qualidade da decisão aparece na capacidade de justificar a escolha a partir de requisitos observáveis e compreender os compromissos assumidos.

Não confunda

“Banco relacional” descreve uma abordagem de dados. “PostgreSQL” é um SGBD concreto que implementa essa abordagem e oferece recursos adicionais.

Síntese conceitual

O que precisa permanecer depois desta leitura

Os pontos abaixo formam a base para compreender o restante da disciplina.

01Arquivos não são “errados”

Eles continuam úteis; um SGBD ganha importância quando o estado precisa ser compartilhado e confiável.

02Banco ≠ SGBD

O banco contém o estado organizado; o SGBD oferece a infraestrutura para administrá-lo.

03O sistema conhece sua estrutura

Esquemas e metadados retiram parte da descrição dos dados de dentro do código das aplicações.

04Abstração cria camadas

Usuários, estrutura lógica e armazenamento podem ser tratados em níveis diferentes.

05Estrutura ≠ estado

Esquema descreve como o banco é organizado; instância representa os valores existentes em um momento.

06Independência reduz acoplamento

Mudanças físicas e, em menor grau, lógicas podem ser absorvidas sem obrigar alterações em todos os consumidores.

07Modelo ≠ produto

Relacional, documental, chave-valor e grafos são formas de organizar dados; produtos concretos implementam essas abordagens.

08Dados representam um domínio

O modelo seleciona propriedades relevantes da realidade; ele não se confunde com a própria realidade.

09Escolha exige justificativa

A tecnologia deve responder aos requisitos de estrutura, consulta, integridade, concorrência, segurança e evolução.
