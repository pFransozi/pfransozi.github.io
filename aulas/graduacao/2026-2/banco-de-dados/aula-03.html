Modelo relacional

Agora damos nome às peças

Uma tabela relacional não é apenas um quadro de linhas e colunas. Ela representa uma relação definida por atributos, domínios e um conjunto de tuplas.

RELAÇÃO: CLIENTEexemplo visual
id_clientenomecidade
1AnaCuritiba
2BrunoColombo
3CarlaCuritiba
Relação = CLIENTE Atributos = id_cliente, nome, cidade Tupla destacada = (2, Bruno, Colombo) Coluna destacada = atributo id_cliente
Grau 3 atributos Cardinalidade 3 tuplas neste momento
RelaçãoO conjunto estruturado

Representa um tipo de fato ou objeto do domínio por meio de atributos e tuplas.

AtributoUma característica

Corresponde a uma propriedade que queremos registrar, como nome, cidade ou data.

TuplaUma ocorrência

É uma combinação de valores que representa um registro da relação.

DomínioValores admitidos

Define o conjunto de valores considerados válidos para um atributo.

GrauQuantidade de atributos

Na relação CLIENTE acima, o grau é 3.

CardinalidadeQuantidade de tuplas

Na instância mostrada acima, a cardinalidade é 3.

Não confunda:

Grau descreve quantos atributos formam a relação. Cardinalidade descreve quantas tuplas existem naquele estado da relação.

id_pedidodatatotal

10212/08/202675,00

Identidade

Por que uma linha precisa ser única?

Uma tupla deve representar uma ocorrência distinguível. Se não conseguimos identificar exatamente qual ocorrência estamos tratando, operações simples se tornam ambíguas.

Sem identidade confiável

nomecidade
AnaCuritiba
AnaCuritiba

São duas clientes diferentes com os mesmos dados visíveis ou um cadastro repetido?

→

Com identidade explícita

id_clientenomecidade
101AnaCuritiba
205AnaCuritiba

Agora cada ocorrência possui uma identidade própria, mesmo quando os demais dados se repetem.

Ideia central:

Uma linha precisa ser distinguível para que o banco possa identificá-la, atualizá-la, removê-la e referenciá-la sem ambiguidade. É esse problema que leva ao conceito de chave.

Chave primáriaA identidade escolhida

Atributo ou conjunto de atributos escolhido para identificar cada tupla de forma única.

CLIENTE.id_cliente
Chave candidataOutra possibilidade válida

Um atributo ou conjunto que também poderia identificar unicamente uma tupla, conforme as regras do domínio.

ALUNO.cpf
ALUNO.email_institucional
Chave compostaIdentidade em conjunto

Quando nenhum atributo isolado basta, a unicidade pode depender da combinação de dois ou mais atributos.

ITEM_PEDIDO
(pedido_id, produto_id)
Chave estrangeiraUma referência a outra relação

Um atributo registra qual tupla de outra relação está associada àquela ocorrência.

PEDIDO.cliente_id
→ CLIENTE.id_cliente
Se duas pessoas podem ter o mesmo nome, por que nome normalmente não é uma boa chave para CLIENTE?

Restrições de integridade

Se o banco consegue armazenar um valor, significa que deveria aceitá-lo?

Um banco consistente não aceita qualquer estado possível. Algumas regras precisam impedir registros sem identidade, valores fora do domínio ou referências que apontam para algo inexistente.

Integridade de entidadeA ocorrência precisa ser identificável

A chave primária não pode deixar a identidade da tupla indefinida.

CLIENTE id_cliente = NULL nome = "Ana"
Integridade de domínioO valor precisa fazer sentido

O atributo deve receber valores compatíveis com as regras definidas para seu domínio.

PRODUTO preco = -350,00
Integridade referencialA referência precisa existir

Uma chave estrangeira deve apontar para uma ocorrência válida na relação referenciada.

PEDIDO cliente_id = 9999 CLIENTE 9999 não existe
Exercício 3 — aceitar, rejeitar ou depende?12 minutos

Para cada situação, classifiquem como ACEITAR, REJEITAR ou DEPENDE DAS REGRAS DO DOMÍNIO. Depois indiquem qual tipo de integridade está envolvido.

  1. CLIENTE.id_cliente = NULL
  2. PRODUTO.preco = -10,00
  3. PEDIDO.cliente_id = 45, mas o cliente 45 não existe.
  4. ALUNO.idade = 15
  5. Duas linhas de CLIENTE com o mesmo id_cliente.
  6. Um PEDIDO com cliente_id = NULL.

Nos itens classificados como depende, escrevam qual regra precisaria ser conhecida antes da decisão.

Redundância e anomalias

Agora vamos fazer a primeira tabela falhar

Voltemos à tabela PEDIDOS. O problema não é simplesmente um valor aparecer duas vezes. O problema surge quando o mesmo fato precisa ser mantido em vários lugares.

PEDIDOSo mesmo fato repetido
pedidoclientetelefoneprodutopreçoquantidade
101Ana9991-1111Teclado120,001
102Bruno9882-2222Mouse80,002
103Ana9991-1111Mouse80,001
104Ana9991-1111Monitor900,001
Redundância problemática:

o telefone de Ana é um fato sobre Ana. Quando esse mesmo fato precisa ser copiado para cada pedido, passa a existir mais de um lugar que precisa permanecer sincronizado.

Anomalia de atualizaçãoAna mudou de telefone

Precisamos alterar várias linhas. Se uma delas permanecer com o valor antigo, o banco passa a guardar versões conflitantes do mesmo fato.

Ana | 9991-1111 Ana | 9777-7777
Anomalia de inserçãoChegou um produto novo

Queremos cadastrar o produto antes de qualquer venda. Mas a estrutura foi construída como se produto só pudesse existir dentro de um pedido.

produto = Webcam pedido = ? cliente = ?
Anomalia de exclusãoBruno cancelou seu único pedido

Se a linha for apagada, podemos eliminar junto o único registro que continha os dados de Bruno.

apagar pedido 102 → some também Bruno?
Exercício 4 — provoque o problema15 minutos

Considere a relação PEDIDOS como a única estrutura disponível para armazenar as informações da loja. Analise cada uma das operações abaixo, observando os efeitos que essa estrutura pode produzir sobre a consistência e a manutenção dos dados.

  1. Atualizar o telefone de Ana.
  2. Alterar o preço do Mouse.
  3. Cadastrar um produto que ainda não foi vendido.
  4. Excluir o último pedido de um cliente.

Para cada operação, elabore uma análise breve indicando:

  • qual fato do domínio está sendo tratado;
  • em quantas tuplas esse fato aparece ou precisa ser modificado;
  • qual tipo de anomalia pode ocorrer;
  • que inconsistência, perda de informação ou ambiguidade pode surgir em decorrência da estrutura atual.

Ao final, sintetize por que a relação PEDIDOS, do modo como está organizada, dificulta a manutenção correta dos dados.

Reorganização

Que fatos diferentes estavam misturados?

Na tabela inicial, uma única linha tentava representar simultaneamente cliente, produto, pedido e item do pedido. Podemos separar esses fatos e conectar as relações por meio de chaves.

CLIENTEQuem compra
  • id_cliente — PK
  • nome
  • telefone
PRODUTOO que pode ser vendido
  • id_produto — PK
  • nome
  • preco
PEDIDOUma compra realizada
  • id_pedido — PK
  • data
  • cliente_id — FK
ITEM_PEDIDOO produto dentro do pedido
  • pedido_id — FK
  • produto_id — FK
  • quantidade

As relações deixam de repetir todos os dados, mas continuam conectadas pelas chaves.

Teste a nova estrutura: onde alteramos o telefone de Ana? Onde cadastramos um produto ainda não vendido? Se apagarmos um pedido, o cadastro do cliente precisa desaparecer?
O objetivo não é criar o maior número possível de tabelas.

É organizar os fatos de modo que cada relação tenha uma responsabilidade clara e que os vínculos entre elas sejam representados explicitamente.

Motivação para normalização

Até aqui reorganizamos por observação. Podemos fazer isso de maneira sistemática?

Sim. A normalização fornece critérios para analisar relações e reduzir determinadas redundâncias e anomalias. Hoje interessa compreender por que esse processo é necessário.

O que já conseguimos perceber

  • um mesmo fato pode estar repetido em várias linhas;
  • uma atualização pode exigir alterações em muitos lugares;
  • inserções e exclusões podem depender de dados que não deveriam depender uns dos outros;
  • uma estrutura pode misturar fatos diferentes.

O que fica para depois

As formas normais, dependências funcionais e critérios formais de decomposição serão estudados em uma aula específica de normalização.

Hoje: reconhecer o problema e justificar por que uma reorganização é necessária.
